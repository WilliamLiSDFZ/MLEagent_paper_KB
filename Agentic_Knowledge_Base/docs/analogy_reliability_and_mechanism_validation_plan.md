## 3. P0：报告交付

### 3.1 明确运行证据的格式

为运行事实增加显式 `runtime_evidence: list[str]`，与机制现有同名字段保持一致。一条事实可以引用多条路径；`evidence` 留作人类可读说明。任务事实、代码事实仍分别使用其现有说明和代码锚点。

packet 在展示 runtime 数据时同时提供实际可引用的路径示例。新契约采用 `.0` 形式表示数组项；路径必须指向**本次真正展示给模型**的非 unknown 值，不能引用只存在后台、被裁剪掉的数据。

建议采用兼容的报告修订标记，例如 `report_schema_revision=2`，与现有 `context_version=2` 分开。旧保存报告继续由旧契约读取；不批量改写历史报告。新输出在规范化后统一校验。

示意：

```json
{
  "statement": "最佳检查点的分组权重仍为均匀分布",
  "source": "runtime",
  "evidence": "引用本次展示的状态观测；不据此直接断言原因",
  "runtime_evidence": ["mechanism_observations.dual_controller.weights"]
}
```

上例路径只是拟议接口示意，实际必须由 packet 提供，不允许模型按名称猜测。

兼容层可以明确转换旧报告的单条点分路径，以及等价的数字数组下标写法；若支持历史 `;` 分隔写法，必须严格拆分、逐条校验、记录原文与规范化结果，不能只取第一条通过的路径。错误、缺失或不可见引用仍需修正。

### 3.2 返回能直接修正的错误

拒绝响应统一为结构化条目：`code`、`location`、`received`、`expected`、`repair_hint`。例如指出 `observed_facts[2].runtime_evidence[1]` 不存在，而不是只返回“必须为可用路径”。

按错误类型给出帮助：

| 错误 | 应反馈的内容 |
|---|---|
| Runtime 路径错误 | 具体字段、合法写法、该段已展示的候选路径 |
| 论文 quote 不匹配 | paper/read 身份、必须引用本 episode 返回正文或摘要的说明；可以重新读证据或删除该主张 |
| 代码引用未覆盖 | node/hash/行号哪里不匹配，以及实际已读范围 |
| 缺少条件或验证计划 | 精确到机制和字段 |
| 报告长度超限 | 实际长度、上限以及可完整删除的低优先级机制 |

只有长度错误才提示压缩报告。论文引用继续核验实际返回文本，不自动改写引文、不替模型生成新的证据。源码工具更明确提示 symbol 与行范围互斥，并提供正确请求形状；不会同时提交这两种选择器。

不把“整份共享事实有错”改成“静默删除后当作全通过”。目前没有完整的事实到机制依赖图，自动删除可能让下游机制失去依据。可继续保留已独立通过校验的完整机制，但必须明确记录部分接受、删减项与原因；不能静默把引用失败的全文机制改标为摘要机制。

### 3.3 14 轮内预留修正机会

默认安排如下：

| 模型响应轮次 | 行为 |
|---|---|
| 1–11 | 阅读、检索、源码核查；允许随时提前提交 |
| 12 | 若尚无可交付报告，强制第一次提交 |
| 13 | 有错误时修正；必要时允许一次针对已知证据的补读，不再发散搜索 |
| 14 | 强制最后一次提交或明确放弃 |

配置建议为 `report_reserve_turns=2`，首次强制提交轮次由 `max_turns - report_reserve_turns` 推导，并校验小预算情形。提前提交失败也进入修正流程，不必继续耗尽阅读轮次。

轮次数和上下文空间都要预留。新增证据返回前估算后续提交与错误反馈的空间；空间紧张时提前进入提交阶段。继续沿用现有 Responses 调用与状态续传规则，不裁断工具调用配对或 opaque response items。到达实际上下文/时间限制仍不能完成时明确记录原因，不追加无上限重试。

### 3.4 记录交付结果，区分主动放弃与失败

新增或扩展 `submission_attempts` 记录：提交轮次、报告契约版本、原始/规范化报告、字段级问题、接受/删除的机制、报告长度、是否处于修正阶段及耗时。保留机制原始索引到最终 `mechanism_id` 的映射。

最终状态区分：

- `accepted_complete`：提交内容全部合法。
- `accepted_partial`：仅部分完整机制通过，明确记录删减项。
- `abstained`：合法地判断没有合适建议，并说明原因。
- `failed`：格式、证据、预算或调用故障导致未交付。

旧 `ok` 字段保留供旧分析读取，新统计使用明确状态；不能把主动 abstain 算成系统故障，也不能把 partial 当作零问题交付。

## 4. P1：先核查当前实现，再提出新机制

### 4.1 在现有循环中加入诊断要求

analogy 在建议增加新算法前，先区分三个问题：

1. 当前实现是否按已有设计执行？例如状态是否写回、更新函数是否真的被调用。
2. 更新条件是否满足？例如样本对是否存在、是否达到 warm-up 或更新周期。
3. 在实现和前提成立后，优化目标或算法是否仍有可改进空间？

通过现有源码工具和下面新增的状态观测完成，不新增必经的 LLM agent，不开放任意 shell。缺少证据时明确列为假设；“权重均匀”不能直接推出“样本不足”或“需要更复杂采样”。

实现 bug 的发现放在代码/运行事实及诊断中，修复建议可直接传给 planner/reviewer，不要求为普通代码修复强配一篇论文。论文机制仍遵守论文证据契约；日志中区分修复已有实现与引入新方法。

### 4.2 给选中的机制增加小型检查契约

在现有 `analogy_adoption` 与交接中补充可检查条件，传给 **planner → coder → code review**。当前 code review 主要收到任务和源码，没有收到完整的 selected mechanism，应补齐这一断点。

检查契约至少包含：机制 ID、执行源码位置、观察的真实对象/状态、触发条件、预期关系、不适用条件、观察窗口和成本上限。它表达待验证的主张，不能直接写成 `passed=true`。

首版确定性数值检查限于有状态更新；队列只检查可用同一套小状态接口表达的占用/指针关系。梯度和 optimizer 连接先作为 reviewer 的检查项，不在本轮搭建通用自动梯度验证系统：

| 类别 | 检查内容 | 避免的误判 |
|---|---|---|
| 状态更新 | 计数器、EMA、动态权重等在触发前后的实际值 | 风险相等、warm-up 未结束、空 mask 时可以不变 |
| 缓存/队列 | 入队前后占用/写指针、有效输入数量 | 队列已满时长度可以不变，应检查写指针或内容摘要 |
| 梯度与优化器连接（本轮仅审查） | 被训练参数是否进入 optimizer、所需分支是否保留梯度路径 | 不以 AST 或 reviewer 的判断声称已经动态验证；冻结或条件分支需声明 |

依赖很长训练才显现的效果、不能低成本观测的机制标记为不支持或证据不足，不硬造一项检查。一般模型、数据和推理代码仍由现有 runtime/代码检查负责。

### 4.3 静态风险提示与真实状态观测

**静态提示**只解析源码，不 import 候选：优先标记类似 `state[mask].add_(...)`、`state[mask].mul_(...)` 的可疑写法。参数是否实际接入 optimizer 等复杂动态关系由 reviewer 核查，不能根据简单 AST 模式断言。AST 模式本身不是证明，不自动改写索引。

**状态观测**绑定真实训练对象。由框架读取有限的张量/计数器并计算变化，生成代码不能通过打印或返回一个 `pass` 字符串让检查通过。对具有清零/提交阶段的控制器，需要围绕实际更新/commit 位置分别记录输入资格、更新前状态和提交后状态，不能只在每步末尾看到计数归零就判失败。

在 code review 后冻结执行源码 hash；绑定的对象、检查调用位置和观测都与 node/hash 关联。不能检查独立 toy 实现后宣称真实训练机制生效。

这仍是协作式 instrumentation：错误绑定可能漏检，LLM reviewer 也不提供形式化保证。因此成功状态只表示“在该次观察窗口与声明条件下看到了所要求的关系”，不表示完整算法正确或必然提升分数。离线回归测试另外使用由维护者定义的固定输入和判定，不能由候选自行定义全部验收条件。

### 4.4 检查成本与副作用

默认在前 5/10/20 次真实 optimizer update 的少量位置采样，并在第一次正式验证前汇总。可以根据机制 warm-up 声明推迟，不能为了等待触发强制增加训练步数。

- 首版每候选检查的额外 CPU/观测预算建议 **30 秒**，可配置硬上限 **60 秒**；累计受现有 candidate 和 run deadline 约束。
- 只复制小状态或有界摘要，限制注册字段数、元素数与落盘大小；不额外跑完整 validation/test inference。读取器只支持已知安全的数据字段/容器，不遍历任意 property 或执行模型生成的判定回调。
- GPU 对象在候选已分配的那张卡上观察，耗时包括必要同步，不新增 GPU worker，也不按 A10/L4 写不同策略。
- 检查不调用 optimizer.step、不改变原状态、不消耗正式训练 RNG。不在活跃模型上注入虚构样本来证明会更新。接近最终结果保存预留时间时停止可选检查，保存完整结果优先。
- 隔离 CPU 探针只用于已有明确接口的小组件或离线回归，超时/不支持记为 inconclusive；不执行整个候选顶层代码，不重新加载 backbone。

### 4.5 首版采用观察模式，不新增自动惩罚

输出区分 `observed_match`、`observed_mismatch`、`inconclusive`、`unsupported`、`probe_error`，同时保存触发情况与数值证据。额外记录 `binding_verified/binding_unverified`；不能确认绑定参与真实训练时，不输出强验证结论。`inconclusive` 不是成功，也不是候选训练失败。

首版建议 **observe**：

- 明确运行异常继续按现有逻辑进入 debug。
- 机制状态不符合预期时落盘，向下一次 analogy/planner/reviewer 提供，不仅埋在终端日志里。
- 不因此直接改 scalar score、不作 reward penalty、不删除有效快照，也不自动把普通未触发情况转为 buggy。
- 不在同一候选里追加无限修复重试。修复沿用已有 debug/improve 搜索过程。

选择观察模式意味着首版不会自动中止所有“可训练但机制不活跃”的候选；节省主要来自执行前审查和后续避免重复误诊。积累误报/漏报数据后，再单独评估仅对可靠数值矛盾启用提前终止。自动 early-stop 不作为本次默认行为。

### 4.6 与快照、其他任务的关系

机制观测必须带观测时的 optimizer step。下一轮 packet 同时展示所选快照步数及机制观测窗口，不能把晚于最佳快照的观测当作该快照的已证事实。

建议落盘为 `logs/mechanism_checks/<node_id>.json`，handoff 保存引用，context 展示经过预算控制的摘要；原始数值证据保留在对应记录中。候选级更新 hash、观测 step、选中快照 ID 与时间都必须保留。

通用检查器建议独立于 Jigsaw scorer 和 `CandidateSession` 实现，提供任务无关的观察接口；CandidateSession 只桥接 step/validation 时机。其他任务可先使用同样的静态审查和源码/检查契约，动态检查在绑定真实训练 hook 后可复用；未绑定时明确 unavailable。

这不意味着现有 Jigsaw candidate runtime 自动支持所有任务的评分、切分和快照恢复；新的任务适配器仍属于独立工作。

## 6. 验收与回放

### P0 离线验收

- 使用本批失败报告、当时的可见 runtime packet、源码 ledger 和全文阅读记录建立 fixture，不重新检索替换证据。
- 合法单路径、多路径、数组下标按新契约可表达；非法、不可见、unknown、错 node/hash/行号或未读引文仍被拒绝。
- 第 12 轮提交失败后，第 13/14 轮具有可执行的修正机会；总轮次和上下文上限不超配。
- 提交成功、部分成功、主动放弃、最终失败都能统计；日志保留完整机制映射。
- 覆盖 code review nullable/schema 及现有 Responses 工具续传回归，避免再次引入此前启动错误。

### P1 离线验收

- 用 S57/S59 的实际错误方法及最小修正版做成对 CPU fixture：错误版本必须暴露不写回，修正版在触发条件成立时出现真实变化。
- 空 mask、相等风险、warm-up、队列满、冻结参数等合法场景不能被误报成确定故障。
- 检查源码/hash 不匹配、绑定缺失、CPU 不支持、超时与部分日志时，明确给出证据不足或探针错误。
- 检查不得改变正式训练 state/RNG，超时不扩充预算；检查结果不能替代 scalar metric 或污染快照有效性。
- 包含一个非 Jigsaw 的小型 CPU 训练 fixture，证明检查器与任务评分解耦，而不是宣称所有任务的训练 loop 都已自动接入。

### 有界真实回放

完成离线检查后，用隔离目录和已缓存论文/源码，最多回放本批 26 个历史 episode 各一次；其中 6 个终局失败是重点。使用现有 Sol 配置，回放日志与原始 run 分离，不修改历史 corpus、快照或评分。

先以修正那 6 个失败 episode 为小批验证，再决定是否执行其余 20 个。报告完整/部分交付率、主动 abstain、失败原因、首交轮次、修正次数、token 和时间，不承诺仅靠小样本达到某个成功率，更不把一次回放成功当成分数提升。

如结构性错误仍重复出现，先修复并重跑对应 fixture；不靠一遍遍重试整个 26 个 episode 挑成功结果。

## 7. P2：怎样验证 improve analogy 是否有收益

建议先做小型固定父候选实验，再扩展整套搜索。

选取已有三个 seed 的第一个 F draft 作为父候选，选择规则只使用 public 状态与预先约定的位置，不按 private 分数挑选。每个父候选对比：

| 条件 | 普通 improve | Analogy improve |
|---|---|---|
| 父源码、public split、允许的历史信息 | 相同 | 相同 |
| 模型、backbone 与初始化方式 | 固定 | 固定 |
| 候选训练/验证预算、GPU 型号、执行槽 | 相同 | 相同 |
| 通用代码审查与机制观察模式 | 相同 | 相同 |
| 论文检索/全文及其结构化建议 | 关闭 | 开启 |

需要明确：这项比较衡量**在一个已由 draft analogy 引导的共同父候选上，增加 improve analogy 的边际收益**，不估计整个 F 流程的总收益。

若要从父模型继续训练，两臂必须有同一份可恢复的 optimizer/scheduler/RNG 状态；当前保存物主要保证推理恢复，不能默认满足完整训练续跑。因此首版优先让两臂从相同预训练初始化、按同一规则训练各自改写的代码，固定输入条件；不声称是在完全相同父训练状态上 resume。

先 3 个父候选 × 2 条件作运行可行性试验；要估计效果，应增加预先指定的生成/训练重复，而不是拿这 6 个候选直接宣布统计显著。记录 public/private 分数、检查状态、失败率、实际 optimizer steps，以及包含检索与修正的总墙钟和 token 成本。Private 分数只用于事后评估。

如需回答整个流程中 draft/improve 各自贡献，再另做 A（无 analogy）/E（仅 draft）/F（draft+improve）配对搜索；固定模型版本、GPU 类型和基础运行逻辑，单独展示新批次，不借历史 baseline。该完整实验矩阵可后续确定，不在本次方案中自动新增或 apply Job。

## 8. 同步、回退与审批边界

获批实施时，P0 与 P1 分开形成可追踪变更，各自完成对应测试。采用 Git 同步固定提交；有实验运行时使用独立 checkout，保证 Job 的入口路径与 `REPO_DIR` 都指向同一提交，不在活跃共享目录上 pull 覆盖。旧 Job 不追写新设置。

这次推荐审批 **P0 + P1 observe 模式 + 对应离线验证和有界 CPU/LLM 回放**。自动 early-stop、额外全局 web search、模型切换、MLEbench 评分修改、GPU 调度重构、所有任务的新 adapter、自动 apply 实验不包含在此范围。

审批后先完成 P0 验收，再接入 P1；若某项通用动态检查不能可靠绑定真实对象，保留其静态提示和 unavailable 状态，不用伪造通过来补齐功能。
